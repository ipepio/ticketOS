# P1–P3 feature backlog

Each item becomes a separate tracker issue when implementation begins. The
acceptance criteria define the first vertical slice; expand only through an ADR
or a follow-up item.

## P1 — Full Service Desk

### P1-01 — Business Calendars and SLA

**Status:** ✅ Done
**Depends on:** P0-03, P0-04, P0-08. **Seam:** SLA. **ADRs:** 0016–0019, 0045, 0054.

**Tasks:** implement reusable Business Calendars; Queue selection; versioned SLA
Policies by Queue/Priority; first-response/resolution targets; risk/breach jobs;
explicit reassessment and resolution-cycle history.

**Acceptance criteria:** known working-hours examples calculate exact target
timestamps; `Pending` pauses resolution and `Open` resumes it; only first public
Agent Message completes first response; Queue/Priority changes do not rewrite an
active target without an explicit audited reassessment; risk/breach notifications
are idempotent.

### P1-02 — Versioned Forms and configurable Ticket Types

**Status:** ✅ Done
**Depends on:** P0-03, P0-04. **Seam:** Forms & Catalog; Workflow. **ADRs:** 0020,
0021, 0042, 0054.

**Tasks:** implement Fields, draft/published Form Versions, supported field type
validation, Type/Form defaults, typed answer storage, authorized answer update,
and historical rendering.

**Acceptance criteria:** publishing an edit creates a new Form Version; existing
Tickets retain original labels/options/answers; invalid typed answers are
rejected through the Forms interface; answer updates create auditable history;
Forms cannot expose inaccessible User/Organization references.

### P1-03 — Automation Rules

**Status:** ✅ Done
**Depends on:** P0-04, P1-01. **Seam:** Automation. **ADRs:** 0022, 0023, 0054.

**Tasks:** implement Rule configuration, event/condition evaluation, bounded
actions, deterministic ordering, causal-chain idempotency, depth limit, audit,
retry/dead-letter view.

**Acceptance criteria:** an eligible rule moves/assigns/updates a Ticket and
records its result; one causal chain cannot execute the same Rule twice; a loop
is blocked with observable reason; unauthorized/invalid configured action is
rejected; failed idempotent action retries without duplicate Timeline effects.

### P1-04 — Knowledge Base and Search

**Status:** ✅ Done
**Depends on:** P0-02, P0-05, P0-06. **Seams:** Knowledge Base; Search. **ADRs:**
0024, 0040, 0054.

**Tasks:** implement Article revisions/draft/publish/audience/category;
authorization-aware PostgreSQL search; public/authenticated/internal rendering;
article attachment support after the P0 lifecycle is generalized.

**Acceptance criteria:** public users see only published public Articles;
authenticated Requesters cannot retrieve internal content or snippets; Agents can
draft while publication requires the configured Capability; a historic published
revision remains attributable; search never leaks inaccessible titles/snippets/counts.

### P1-05 — Notifications, SSE, i18n, and observability completion

**Status:** ✅ Done
**Depends on:** P0-05, P0-08. **Seams:** Notification; authorized SSE stream.
**ADRs:** 0037–0039, 0047, 0054.

**Tasks:** implement preference model, in-app inbox, email/digest worker jobs,
authorized SSE reconnect/replay, Spanish/English notification templates, and
P1 OTel metrics.

**Acceptance criteria:** an assignment/direct reply/mention creates exactly one
eligible notification according to preference; a User cannot subscribe to another
Workspace’s SSE events; reconnect cannot expose skipped inaccessible events;
urgent defaults and digests follow ADR 0054; system copy/local dates render in
Spanish and English.

### P1-06 — Versioned API and signed Webhooks

**Status:** ✅ Done
**Depends on:** P0-02, P0-04, P0-08. **Seams:** Integration. **ADRs:** 0035,
0036, 0054.

**Tasks:** implement REST resource contracts, service-token issuance/revocation,
Capability enforcement, event selection, signed delivery, retry/dead-letter/
replay, API compatibility documentation and rate limits.

**Acceptance criteria:** a service token can perform only granted Workspace
Capabilities; revoked tokens immediately fail; each webhook delivery includes
unique event ID and verifiable HMAC timestamp/signature; retry produces at-least-
once delivery without duplicate downstream domain mutation; API never returns
Internal Notes to an unauthorized token.

## P2 — Governed service operations

### P2-01 — Service Catalog

**Status:** ✅ Done
**Depends on:** P1-01, P1-02. **Seam:** Forms & Catalog. **ADRs:** 0041–0043,
0045, 0054.

**Tasks:** implement Catalog Item publication, Type/Form/Queue/Priority/SLA
selection, requester portal catalog journey, availability rules, and creation
of appropriately configured Service Request Tickets.

**Acceptance criteria:** selecting a published Item creates a Service Request
with its configured Form/Queue/Type/SLA activation rule; unavailable Items
cannot be requested; history shows the Item/version used; direct form tampering
cannot select unauthorized Queue or policy.

### P2-02 — Approval

**Status:** ✅ Done
**Depends on:** P2-01. **Seam:** Approval. **ADRs:** 0043–0045, 0054.

**Tasks:** resolve approvers, execute sequential steps, support `any-one` and
`all`, record decisions, gate fulfillment, send notifications/reminders, and
handle rejection/cancellation.

**Acceptance criteria:** an `any-one` step completes on one eligible approval;
an `all` step requires every resolved approver; an ineligible decision is
rejected; rejection ends policy and moves Ticket to configured terminal Status;
SLA activation follows the Catalog Item setting; every decision is audited.

### P2-03 — Reporting

**Status:** ✅ Done
**Depends on:** P1-01, P1-03, P1-06. **Seam:** Reporting. **ADRs:** 0046, 0054.

**Tasks:** define report dimensions/measures, saved Workspace reports,
asynchronous materialization, CSV export, limits, and authorization checks.

**Acceptance criteria:** a report returns correct known aggregates for Queue,
Priority, Type, Status Category and SLA state; unauthorized data never affects
rows, totals, or CSV; expensive runs are asynchronous and observable; CSV
export respects caller capability and locale-safe formatting.

### P2-04 — Retention, Legal Holds, and MFA administration

**Status:** ✅ Done
**Depends on:** P0-06, P0-08. **Seams:** Retention; Identity. **ADRs:** 0026,
0049, 0054.

**Tasks:** implement Policy configuration, Legal Hold capability, archival,
erasure/anonymization workflow, attachment/object cleanup, backup expiry policy,
TOTP/WebAuthn enrollment and privileged enforcement.

**Acceptance criteria:** held Ticket data is skipped by purge; releasing a hold
restores eligibility; retention removes/anonymizes content plus Attachment while
preserving minimum audit evidence; privileged MFA policy blocks unenrolled users
without breaking recovery; all destructive actions are auditable.

## P3 — Platform expansion epics

### P3-01 — Omnichannel support (D)

**Dependencies:** P1-05, P1-06. **Seams:** Email-like Channel adapter; Ticket.

**Tasks:** define channel identity and delivery adapter contract; implement chat
first; add conversation session rules, routing, rate limits, attachments, and
WebSocket adapter; later add WhatsApp/social providers.

**Acceptance criteria:** a channel Message becomes the same authorized Ticket
Timeline Message model as email/portal; retries cannot duplicate it; channel
identity never gains broader access than the matching Requester; agent reply
uses the correct source channel and is audited.

### P3-02 — Project/issue tracking (B)

**Dependencies:** P1-02, P1-03, P2-03. **Seams:** Project module; Ticket.

**Tasks:** introduce Project, backlog, board, sprint, epic, issue relationships,
and project-specific views without reusing Queue as Project.

**Acceptance criteria:** Project membership/visibility is enforced independently
of Queue; issue workflow remains compatible with Ticket Timeline/audit; board
operations do not bypass Workflow transitions; a Project report cannot leak
another Workspace.

### P3-03 — Problem, Change, and CMDB/asset modules

**Dependencies:** P2-02, P2-04. **Seams:** Problem; Change; Asset modules.

**Tasks:** model linked Incidents/Problems, governed Changes, Configuration
Items and relationships; reuse Approval, SLA, Audit, and Attachment interfaces.

**Acceptance criteria:** a Problem can link multiple Incidents without changing
their individual histories; Change approval gates execution; Asset access is
Workspace-authorized; no module duplicates Ticket/SLA/Approval policy.

### P3-04 — Hybrid platform (E)

**Dependencies:** real adoption evidence from P0–P3. **Seams:** Workflow,
Forms & Catalog, authorization.

**Tasks:** identify proven variations, add configurable roles, broaden Type
Categories/workflows, and expose extension points only where two real adapters
or callers justify them.

**Acceptance criteria:** each new extension removes duplicated caller complexity;
existing A/D/B behavior remains unchanged through module-interface regression
tests; no arbitrary code execution is introduced into Automation.
